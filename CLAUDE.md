## HARD RULES — read first, never skip (violations caused real damage)
1. **Close-out block (trigger: merging a code branch to main, or the user says it's done/live, or ~15 turns in one chat). Docs-only commits to main (🔒 lock line, Relay, review files) never trigger it (set 152 B1). At ~15 turns mid-set: finish the current step, push, write the WIP branch + next step in the Relay, then close out — the new chat continues the same set (set 152 C1).** Run the `close-out` skill (.claude/skills/close-out/SKILL.md): update + push claude/handoff.md, then the Thai block (ควรเปิดแชทใหม่ได้แล้ว · user todo · model · paste-message). It starts with a skill check: should this chat's procedure become a skill? → ask the user A1/A2/A3 (set 155). Never continue into new work in the same chat after this block. **Publishing the set's own work is NOT new work (user rule set 184 B1): ask about publishing in the set's first question round and publish before the close-out block, in the same chat.**
2. New file in src/core or src/game = add it to `CORE` in src/build.mjs in the same commit (a missing entry only breaks the built page, not the tests).
3. **Merge gate (rule 31 Oct, after set 62 shipped a broken build):** first run `cd src && node tools/bootstrap.mjs setup` (build + unit tests, ~3 min) until it passes, fixing every failure; only then run the full gate ONCE (rule 5 Nov: never use the slow gate to find test failures). Before merging to main, run `cd src && node tools/bootstrap.mjs gate` (build + tests + ui_smoke on the BUILT pages, installs python playwright if missing, ~4 min, prints GATE: PASS/FAIL; FAILS [] ERRORS [] required). The gate skips unit tests when setup passed on the exact same files < 6 h ago (round 2 D1, set 139: any edit → tests run again; `gate --full` forces; CI always runs everything). This is the ONLY full statement of the gate rule; other docs point here (set 153 K1). Unit tests alone are not enough — they run on source, not on the built html. If ui_smoke cannot run: set it up first (cloud: `pip install playwright`; ui_smoke uses /opt/pw-browsers/chromium); if still impossible, tell the user in Thai and wait for their decision. Never merge or publish silently untested. **Publish gate:** the chat that publishes must first `git fetch`, build from the LATEST main, and get GATE: PASS on that exact commit — the paste-message for the old chat says so; it reports the gate result in the Relay line.
4. handoff.md says "บาลานซ์: กำลังปรับ" = do not import, do not measure. Overrides everything.
5. Never fix before the cause is known with evidence (how: skill `find-cause`, set 163). Tests/page failing or untestable = do not publish, tell the user immediately.
6. **Check before tuning (user rule 7 Nov, set 130):** any task that touches game values (characters, tribes, rules, runes, bosses, mode settings, bossrun/botgen/import) starts with: get a fresh AMCFG1 (main account = read the Balance Room db yourself after the user says they pressed 💾; 2nd account = ask the user to paste it; user rule set 166) → `cd src && node tools/cfgdiff.mjs <file> --md claude/review-YYYY-MM-DD-cfgdiff-revNN.md` (NN = AMCFG1 rev) → show the user every differing cell and ask, per cell or per group, which side wins (Balance Room or game) → only then edit → publish the Balance Room → tell the user exactly which cells they must set back in the Balance Room (+ 💾). bossrun: run WITHOUT --write first, show the user before/after values, write only after the user agrees. Details: claude/workflow/balance-import.md §00.
7. Validate external data before use · no innerHTML with external text, no eval, no scripts from other sites. (= part ③ of HARD RULE 9.)
8. **Ripple check (user rule set 186 A1 — fixes kept missing linked spots):** before committing any change to behaviour, a value, a name, player text, a save format, a rule id or a decision, grep every changed term (old spelling too) across src + claude docs + tests and walk the map in claude/workflow/ripple.md; fix every copy or say why not; the commit message carries a `ripple:` line. Steps live in merge-code / rule-change / balance-import / ui-work / find-cause.
9. **Security at every step (user rule set 190 C1 — creators' work gets stolen/attacked):** ① no secrets in repo/commits/docs/chat (keys only via request_credential; secret grep before every commit) ② no outside code/addon/package/asset/font without source + licence + credit + the user's OK; pin versions ③ validate all external input (HARD RULE 7; Godot: never load() player files) ④ shipped pages/builds carry only the game (no docs, tools, tests, debug, source maps; Godot release + PCK encryption, key never in repo) ⑤ 2FA on GitHub/itch.io/Google, repo private ⑥ every plan step has a security line. Details + where each part is checked: claude/workflow/security.md.

## Language
- Think and write in English, including every doc Claude reads (claude/handoff.md, pending.md, ops-rules.md, workflow*, backlog.md, budget-notes.md, measure-log.md).
- **Reply to the user in Thai**, short, no preamble, no recap. After the 3-line header below, details start with what the user must do/decide; explain technical terms.
- **Reply format (user rule 8 Nov, set 150 B1):** every reply starts with 3 short Thai lines, then details below: ① ทำแล้ว/พบ: what was done or found · ② ต้องตัดสินใจ: what the user must approve/decide (or "ไม่มี") · ③ ไม่แน่ใจ: what Claude is unsure about (or "ไม่มี"). The user may stop reading after line 3.

- Docs the user reads stay Thai: combat-rules, tribe-rules, shop-merge-rules, build-plan. Never translate them. Files still in Thai that the user doesn't read: translate to English when opened.

## Decisions
- **Ask everything up front, then run to the end (user rule 8 Nov, set 150 A1):** at the start of a task set, ask ALL questions needed to finish it in one go (one AskUserQuestion round, more calls only if > 4 questions); after the answers, work to the end without stopping. Stop mid-task only when: publishing an artifact · changing game values / writing the Balance Room db (HARD RULE 6 per-cell picks and bossrun before/after still apply — ask those up front when the data is already known) · a test/gate fails or the cause is unknown (HARD RULE 5) · something irreversible or outside the agreed scope.
- **Weekly review (set 150 D1 · skill set 154):** when the user says "รีวิวสัปดาห์" (planned every Friday) or asks to audit the workflow/rules, run the `weekly-review` skill (.claude/skills/weekly-review/SKILL.md): user corrections + waste of the week, then the workflow audit checklist (rule vs rule, doc vs code, stale text, review hygiene) → claude/review-YYYY-MM-DD-weekly.md → A/B per change → edit only after approval.
- **New tools:** prefer written instructions (topic file / skill) over new scripts; write code only when instructions cannot do the job, keep it small (set 150, habit 7).
- Design/rules: offer 2–3 options + a recommended one, wait for confirmation (skill `rule-change`, set 158).
- **Every time the user must pick (always-on, not topic-only):** label A/B… with options A1/A2…, explain in text first, THEN call AskUserQuestion buttons (max 4 questions per call; more → next call). Details: claude/workflow/replies.md. Several topics in one message = ask once, do all in one pass.
- Small things (text, colours, button position, internal code): decide and inform.
- The user tunes character stats. New character: propose from the median table. Numbers in skills/rules: always ask first.
- Unbalanced idea / loophole: warn directly first.
- **Conflict check (user rule 7 Nov, set 118 — the user may mistype):** before acting on ANY request, compare it with the current docs/code (rules, settings, earlier decisions). If it contradicts or changes something already decided, STOP and tell the user first in Thai: what exists now (doc + rule id + set), what the request would change, and every side effect/clash it creates — then wait for confirmation. Never silently follow the new wording, never silently keep the old one.

## Token saving
- 1 task set = decide → edit → test → publish once. End of set (or long chat) → close-out block (HARD RULE 1); handoff.md ≤ 1 screen, older content → claude/archive/.
- Tiny fix but heavy search → log in handoff "งานรอรวม". Do pending items when 3 are queued / the same file is already open / user says so. Warn if pending > 2 task sets.
- Read only what's needed, never re-read, never read whole built HTML. Test output: failures only. Subagents only with the user's approval.
- **Proactive token alert (any time):** when the current work starts using many tokens (large files/outputs, repeated searches, long debugging, growing chat) and Claude sees a cheaper way (narrower read/grep, splitting the task, smaller model, new chat, batching, skipping a step), tell the user immediately in 1–2 Thai lines: what is costly + the cheaper option + trade-off. Don't wait for the end of the set; keep working unless the switch needs the user's decision.
- **Proactive workflow advice (user rule 8 Nov, set 139 — widens the token alert):** whenever Claude notices wasted work, a messy/non-standard way of doing something, or a better, faster, cheaper or more orderly method (in code, tests, docs, the gate, the relay, or how the user and Claude work together), tell the user right away without waiting to be asked: 1–3 Thai lines = what is wasteful + the better way + trade-off (+ A1/A2 options if a choice is needed). Keep working on the current task meanwhile; never change rules or process on that advice until the user agrees. Bigger lists go in a claude/review-*.md file named in the Relay block.
